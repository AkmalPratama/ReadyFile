The problem

Files do not fail for lack of effort. They fail on timing.

What happens today

  1. Missing documents discovered late. Officers compare files against checklists held in spreadsheets or email templates. Omissions surface only when an underwriter picks the file up.
  2. Expired documents slip through. A document valid at submission may expire before decision, forcing re-collection.
  3. Rework loops delay processing. Each missing or expired item triggers a borrower request cycle averaging several days.
  4. No single visibility of file readiness. No at-a-glance "decision-ready" status, so files queue that cannot progress.
  5. Inconsistent checklist application. Different officers apply different standards; the audit trail of what was checked, and when, is weak.

What it costs

  • Longer time-to-decision and time-to-disbursement — risking customer drop-off to competitors.
  • Higher operational cost per loan from manual chasing and re-keying.
  • Compliance exposure when stale KYC or income evidence is used in a decision.
  • Underwriter capacity wasted on incomplete files.
ReadyFile sits at one boundary — between intake and underwriting. That boundary is the product, not a feature of it.

How it works

How the engine decides

Item status — five states

  • PRESENT_VALID — uploaded, fresh enough at the decision date
  • EXPIRING_SOON — inside the warning window; still counts as valid
  • EXPIRED — too old, or hard expiry passed; blocks the file
  • MISSING — required item with no uploaded file; blocks the file
  • NOT_APPLICABLE — condition not met, or optional and absent

Freshness, measured at the decision date

With M the max age, H the warning horizon and A the document's age in days:

A > M  →  EXPIRED
M−H ≤ A ≤ M  →  EXPIRING_SOON
A < M−H  →  PRESENT_VALID

The warned range is H+1 days wide, inclusive of both ends. H = 0 warns only at exactly M — it does not disable warnings.

Hard expiry — equality only

expiry < decision  →  EXPIRED
expiry = decision  →  EXPIRING_SOON
expiry > decision  →  PRESENT_VALID

No warning window on this basis — widening it would flag IDs expiring weeks after approval, which no source in BRD §6.2 requires.

Both bases can sit on one rule. Both are evaluated and the most severe wins.

Score and the gate

score = round(valid required ÷ applicable required × 100)
  • EXPIRING_SOON counts as valid for the score
  • Optional and NOT_APPLICABLE items are excluded
  • Any required item MISSING or EXPIRED ⇒ INCOMPLETE
  • Acknowledging warnings can never clear a blocker

Design decision

Deterministic by construction

What the engine cannot do

  • Read the wall clock. No Date.now anywhere in src.
  • Use randomness. No Math.random.
  • Touch the network, the filesystem or the environment. No Node built-in imports at all.
  • Mutate the rule set it was handed — so a sandbox preview can never rewrite history.
  • Depend on input ordering. Items sort by rule id using code-unit comparison, explicitly not localeCompare, because ICU collation varies by runtime locale.

What that buys

  • Same inputs + same rule version ⇒ byte-identical JSON. PC-28 and NFR-02.
  • Any run is replayable from its inputs plus its rule version. PC-30.
  • A rule change is data, not a deployment. Edit-and-rerun measured at 0.015 ms against a two-minute budget. PC-27.
  • Three independent proofs in QA: a static source scan with comments stripped, a behavioural spy that fails if Date.now or Math.random is called even once, and a dependency-manifest check.
  • Every result traces to a named policy line — the answer to incumbents marketing against rules engines (BRD CE-1). We compete on explainability and auditability, not on minimising follow-ups.
